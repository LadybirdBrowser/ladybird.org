### Style and layout no longer wait for JavaScript

Browsers normally run JavaScript, style, and layout on one main thread, one at a time. While a script runs, the page can't update. A few simple animations can keep going on the compositor, but everything else has to wait.

We moved style and layout to their own thread, and paint recording to another ([#12377](https://github.com/LadybirdBrowser/ladybird/pull/12377), [#12400](https://github.com/LadybirdBrowser/ladybird/pull/12400)). They now run at the same time as JavaScript ([#12396](https://github.com/LadybirdBrowser/ladybird/pull/12396), [#12432](https://github.com/LadybirdBrowser/ladybird/pull/12432), [#12460](https://github.com/LadybirdBrowser/ladybird/pull/12460)). If a script asks for layout information, like an element's size, it waits until pending layout work is finished, so it never gets stale data.

So two things now work during a long script:

- **CSS animations keep running while JavaScript is busy.** This includes animations that change layout, like `width` and `font-size` ([#12433](https://github.com/LadybirdBrowser/ladybird/pull/12433), [#12447](https://github.com/LadybirdBrowser/ladybird/pull/12447), [#12451](https://github.com/LadybirdBrowser/ladybird/pull/12451)).
- **`:hover` keeps working while JavaScript is busy.** The render thread finds the element under the mouse, applies its hover styles, starts any transitions, updates the cursor, and draws a new frame. When the script ends, the main thread catches up and fires the hover events ([#12530](https://github.com/LadybirdBrowser/ladybird/pull/12530)).

### A JavaScript JIT

On Linux and macOS, LibJS now compiles hot JavaScript to machine code, on both x86-64 and AArch64 ([#12613](https://github.com/LadybirdBrowser/ladybird/pull/12613)).

We decided against a JIT in the past, and did what we could to push and tune the interpreter instead. It's already competitive, so making it twice as fast would be a huge effort, and that would only turn a 300ms hang into a 150ms hang, which you'd still notice. So we needed an optimizing JIT.

The design is deliberately boring: speculative optimization based on runtime type profiling, like other JavaScript engines. For now, we just want to go reasonably fast.

/>
<img
  class="only-dark"

  style="max-width: 100%;"
  alt="Flow diagram: code starts in the interpreter, moves to a profiling interpreter, then a background compiler, then runs as JIT code. If a guess was wrong, it goes back to the interpreter and gets recompiled."

While code warms up, we record things like which types and object shapes it sees ([#12588](https://github.com/LadybirdBrowser/ladybird/pull/12588)). The compiled code uses those recordings to make guesses, like "this value is always an integer", and inlines small functions ([#12595](https://github.com/LadybirdBrowser/ladybird/pull/12595), [#12598](https://github.com/LadybirdBrowser/ladybird/pull/12598)).

To find bugs during development, we used a fuzzer that ran the same code in the JIT and the interpreter and compared the results ([#12601](https://github.com/LadybirdBrowser/ladybird/pull/12601)).

### A new WebAssembly engine

We replaced our C++ Wasm engine and Cranelift with a new engine that has its own interpreter and JIT ([#12963](https://github.com/LadybirdBrowser/ladybird/pull/12963)). It supports newer parts of WebAssembly that the old engine didn't, like exception handling and GC. On the JetStream 3 Wasm workloads both engines can run, it scores about 7x higher.

In July, we built flap, a small language and compiler for writing LibJS's interpreter. The Wasm interpreter is written in flap too, so one source builds it for x86-64, AArch64, and Windows x64. Hot functions move from there to the JIT, even in the middle of a running loop.

We're making great progress on performance. [JSLinux](https://bellard.org/jslinux/), an x86 PC emulator, now boots Alpine Linux to a shell in 1.8 seconds, while Chrome takes 1.5.

### Security and process isolation

Web pages run in sandboxed renderer processes, so a malicious page that takes over its renderer should be stuck there.

We kept fixing security issues from many sources, including ways around that sandbox. For example, a compromised renderer could ask the browser process to open any file on your computer. Now only a renderer showing local files can read them ([#12582](https://github.com/LadybirdBrowser/ladybird/pull/12582), [#12590](https://github.com/LadybirdBrowser/ladybird/pull/12590)). Renderers could also fake a user click to open popups or read the clipboard. The browser process no longer trusts them on this ([#12597](https://github.com/LadybirdBrowser/ladybird/pull/12597)).

We also split the browser into more processes, so a compromised one can reach less:

- **Cross-site iframes** get their own renderer by default ([#12647](https://github.com/LadybirdBrowser/ladybird/pull/12647)), and so do cross-site popups ([#12296](https://github.com/LadybirdBrowser/ladybird/pull/12296)).
- **Each top-level site** gets its own network process, and the HTTP cache and third-party cookies are kept separate per site ([#13144](https://github.com/LadybirdBrowser/ladybird/pull/13144), [#12424](https://github.com/LadybirdBrowser/ladybird/pull/12424)).
- **Each renderer** has its own audio process ([#12604](https://github.com/LadybirdBrowser/ladybird/pull/12604)) and image decoder ([#12437](https://github.com/LadybirdBrowser/ladybird/pull/12437)).

### Media and Windows

On Windows, video now plays and YouTube works ([#12646](https://github.com/LadybirdBrowser/ladybird/pull/12646), [#13195](https://github.com/LadybirdBrowser/ladybird/pull/13195)). Hardware video decoding moved to its own process and now works on Linux through Vulkan ([#12868](https://github.com/LadybirdBrowser/ladybird/pull/12868)). We also read MP4 files ourselves now instead of using FFmpeg, which fixes problems with seeking and buffering ([#12641](https://github.com/LadybirdBrowser/ladybird/pull/12641)).

### More C++ moved to Rust

LibJS's runtime moved from C++ to Rust just before the JIT landed, so our JavaScript engine is now all Rust, apart from its flap interpreter and the garbage collector ([#12492](https://github.com/LadybirdBrowser/ladybird/pull/12492)). The new Wasm engine is Rust as well. WebGL, 2D canvas, IndexedDB, Streams, and `URL` also moved over ([#12699](https://github.com/LadybirdBrowser/ladybird/pull/12699), [#12935](https://github.com/LadybirdBrowser/ladybird/pull/12935), [#13287](https://github.com/LadybirdBrowser/ladybird/pull/13287), [#13083](https://github.com/LadybirdBrowser/ladybird/pull/13083), [#12998](https://github.com/LadybirdBrowser/ladybird/pull/12998)). We also deleted the C++ style computation, so style is now computed entirely in Rust ([#12346](https://github.com/LadybirdBrowser/ladybird/pull/12346)).
